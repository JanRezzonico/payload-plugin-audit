# Audit Plugin for Payload CMS

`audit-plugin-payload` adds an audit trail to Payload CMS collections. It records who created or updated a document, stores update deltas, and exposes the audit information in the Payload admin panel through read-only virtual fields.

## Features

- Records `create` and `update` operations in a dedicated audit-log collection.
- Stores the user responsible for each operation.
- Calculates update deltas with [`jsondiffpatch`](https://github.com/benjamine/jsondiffpatch).
- Adds a virtual `createdBy` relationship field to audited collections.
- Adds a virtual update history field containing the user, date, and delta for each update.
- Renders update deltas in the admin panel with the included `DeltaViewer` component.
- Supports polymorphic relationships to one or more user collections.
- Allows the log collection, generated field names, access rules, labels, and colors to be customized.

## Installation

Install the plugin in your Payload application:

```bash
npm install audit-plugin-payload
# or
pnpm add audit-plugin-payload
# or
yarn add audit-plugin-payload
```

## Basic Usage

Add the plugin to the `plugins` array in `payload.config.ts`:

```ts
import { auditPluginPayload } from 'audit-plugin-payload'
import { buildConfig } from 'payload'

export default buildConfig({
	collections: [Posts, Users],
	plugins: [
		auditPluginPayload({
			access: {
				manage: ({ req }) => false, // Disable manual logs management
				read: ({ req }) => Boolean(req.user), // Only logged-in users can read logs
			},
			collections: ['posts'],
			userCollections: ['users'],
		}),
	],
})
```

`collections` contains the slugs to audit. `userCollections` contains every auth-enabled collection whose users may create or update an audited document. Both arrays are required and cannot be empty.

After adding or changing the plugin configuration, regenerate Payload types and apply the database schema changes using your normal Payload workflow.

## Generated Data

The plugin creates an `audit-plugin-logs` collection by default. Each log contains:

- `operation`: `create` or `update`.
- `entity`: a polymorphic relationship to the audited document.
- `userId`: a polymorphic relationship to the user who performed the operation.
- `delta`: the `jsondiffpatch` result for updates.
- Payload-managed `createdAt` and `updatedAt` timestamps.

For every audited collection, the plugin also adds these virtual fields:

- `auditPluginCreatedBy`: resolves to the user who created the document.
- `auditPluginUpdateLogs`: resolves to the document's update history, including the user, date, and delta for each update.

The generated fields are virtual and read-only.

## Limitations

Audit logs are generated by `afterChange` hooks, so deletes are not currently recorded.

## Configuration

### State

Use `state` to control the plugin lifecycle:

```ts
state: 'enabled' // default: hooks, logs, and virtual fields are active
```

- `enabled`: records audit logs and adds the virtual fields.
- `inactive`: keeps the audit-log collection and virtual fields but stops creating new logs (disables the `afterChange` hooks).
- `disabled`: leaves the Payload configuration unchanged and disables the plugin entirely.

### Database names

The defaults can be overridden when a migration or an existing naming convention requires it:

```ts
db: {
	collections: {
		logs: {
			slug: 'my-custom-audit-logs-collection-slug',
			hidden: true,
		},
	},
	fields: {
		createdBy: { name: 'myCustomCreatedByFieldName' },
		updateLogs: { name: 'myCustomUpdateLogsFieldName' },
	},
},
```

Changing collection slug or field names changes the database schema and generated Payload types, so keep it in mind and perform database migrations as needed.

### Access control

`access.read` controls who can read audit logs and the generated virtual fields. `access.manage` controls manual create, update, and delete access on the audit-log collection. Keep `manage` as restrictive as possible because users with it can alter the audit trail. It is recommended to set `manage` to `false` and rely solely on the plugin's automatic logging.

### Admin UI

Labels, date formatting, delta badges, and badge colors can be customized through the `ui` option. The client components are also available from the `audit-plugin-payload/client` export:

```ts
import {
	DeltaViewer,
	UpdateDeltaRowLabel,
	UserDescription,
} from 'audit-plugin-payload/client'
```

These components are primarily intended for Payload admin component configuration and are already wired into the generated fields and audit-log collection.

This repository includes a Payload example application in `dev/`:

```bash
pnpm install

pnpm dev
```

```bash
pnpm test # Run unit and integration tests
pnpm lint # Run ESLint
```
